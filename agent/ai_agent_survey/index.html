导读：什么是智能体，现在走到了哪里

一个智能体 = 模型 + 工具 + 循环 + 管理这个循环的程序（harness）。模型负责决定下一步做什么，工具负责把决定变成对外部世界的动作，循环把动作的结果送回模型；harness 决定模型能看到什么、能做什么、什么时候停。能不能用好智能体，主要取决于后三者，而不只是模型本身。

智能体循环

目标 + 上下文→模型：思考，选一个动作→harness：权限检查，执行工具→观察结果写回上下文↺直到完成、失败或需要人确认

这个循环最早由 ReAct 写成"思考—行动—观察"；今天的编码智能体、计算机使用智能体和深度研究智能体仍然是它，只是工具更多、循环更长、上下文管理更讲究。

从一次调用到自主智能体

先用能解决问题的最简单方案（Anthropic）
单次调用分类、抽取、摘要、问答。一次请求、一次回答，最便宜也最好评测。
工作流代码决定步骤：链式、路由、并行、评审—修改。步骤可预知时首选。
智能体模型决定步骤：步数和路径事先不知道，靠环境反馈纠错。编码、研究、操作电脑。
多智能体 / 长时运行多个上下文并行、跨会话持续几小时到几天。开销大，适合能并行拆分的任务。

构件：模型、工具与智能体循环

智能体由什么组成？模型怎样决定下一步、怎样调用工具？

今天的智能体建立在函数调用之上：模型按 JSON Schema 输出结构化的工具调用，宿主程序执行后把结果作为观察送回。三条早期路线汇成了这个形态：推理与行动交替（ReAct），学会何时、如何调用工具（Toolformer、Gorilla、ToolLLM），以及用代码作为动作（PAL、CodeAct）。早期靠提示词实现的规划与反思，大部分已经被推理模型内化；现在的难点是长程：在几十到几百步里保持目标、不重复劳动、及时验证、知道何时停。

工具调用 = 结构化输出 + 执行 + 回传

每个工具有名称、描述和输入 schema；模型可以在一轮里并行发出多个调用，宿主执行后把全部结果放进下一条消息。出错时把错误信息作为结果返回，模型通常能自己纠正。工具的描述写得好不好，直接决定调用质量（为智能体编写工具）。

代码即动作

与其定义几十个 JSON 工具，不如给模型一个沙箱和解释器：CodeAct 发现以 Python 为统一动作空间更强，smolagents、mini-swe-agent（只用 bash）沿用这一思路；LLM-in-Sandbox 发现仅让模型在代码沙箱中探索就能激发通用的智能体能力。

边想边做

推理模型在工具调用之间继续思考（交错思考），比"先想完再做"更能利用观察。但想得多不等于做得好：过度思考在智能体任务中会损害表现，推理力度应按步骤难度分配。

何时停、花多少

循环需要停止条件：任务完成、步数或预算用尽、需要人确认。让模型感知剩余预算能让工具调用更有效（预算感知）；测试时计算同样适用于智能体（智能体的测试时扩展）。

2021 → 2026-04

WebGPT 让模型使用文本浏览器并引用来源；MRKL 把 LLM 作为路由器连接外部模块；HuggingGPT 用 LLM 调度专家模型。规划与反思方向有 Reflexion、Self-Refine、Tree of Thoughts、LATS、Plan-and-Solve；效率方向有 ReWOO（先规划全部调用）与 LLMCompiler（并行 DAG）。2025 年起，工具使用越来越多地由强化学习训练（ReTool、ToolRL、ARTIST），而不是靠提示。API 智能体与 GUI 智能体的分化与融合，是理解第 5、6 章的背景。

最近半年（2026-05 → 2026-10）

橙色为最近半年
  1. 2026-08 → 09打破"想—做—看"的严格顺序。Second Thought 在行动执行、等待观察的同时并行推理；异步智能体让模型边想边做，减少等待工具返回造成的空转。
  2. 2026-10长程失败有了更细的刻画。长程智能体常重复已经做过的工作，DeLoop 把重复动作当作自监督信号来纠正；Interlock 研究为什么每一步局部正确却完不成整体任务；Agent-Reflex 只在关键步骤前反思；工具使用智能体如何失败专门分析改变外部状态（写数据库、发消息）时的失败。
  3. 2026-09从"听指令"到"主动"。主动式智能体基础给出主动性的分层与 Proactivity-Gym；横向与纵向主动性区分"多做相关的事"与"把事做深"。这是个人助理类产品（第 8 章）的核心问题。
  4. 2026-07 → 09长程规划的机制与极限。多轮长程规划的物理学从预训练到后训练追踪规划能力的来源；循环语言模型在组合式工具调用上泛化更好；Marathoner 以超长程自主执行为目标。
  5. 2026-05 → 09工具使用的数据来自合成环境。EnvFactory、WEFT 合成可执行环境做工具使用后训练，无环境 API 数据合成则用世界模型代替真实环境；细节见第 9 章。

实践建议

  • 先给少量、职责清楚、互不重叠的工具；名称和描述写给"第一次见到它的新同事"看。
  • 工具出错时返回可读的错误信息（并标记为错误），不要抛异常中断循环。
  • 设置最大步数、超时和花费上限；无依赖的工具调用让模型并行发出。
  • 任务步骤可预知时，用代码写成工作流，只在需要判断的地方调用模型。

尚未解决

  • 何时先规划、何时直接行动？如何在长程中可靠地检测"原地打转"？
  • 异步、并行行动下，如何保证对外部状态的修改仍然正确、可回滚？

上下文工程与记忆

模型每一步应该看到什么？跨会话应该记住什么？

上下文窗口是智能体唯一的工作记忆，而且有效容量远小于标称长度：信息越多，模型越容易遗漏和分心。上下文工程就是在每一步决定放进什么：稳定的系统提示与工具定义、按需检索的资料、被压缩的历史、写到文件里的进度，以及交给子智能体的独立上下文（上下文工程）。它同时决定成本：前缀稳定才能命中 KV 缓存（Manus 的经验）。长期记忆把经验存在模型之外；最近半年的一个重要发现是，复杂的记忆系统未必胜过朴素检索，记忆的净价值要扣掉构建和检索的成本。

写、选、压、隔

写：把计划、进度、中间结果写到文件或笔记；选：只在需要时检索（"即时"检索而非预先塞满）；压：接近上限时摘要旧轮次、清掉过时的工具输出；隔：把探索交给子智能体，只取回摘要。

为缓存设计

前缀保持不变（系统提示、工具列表固定）、历史只追加不修改、时间戳等易变内容放在后面。缓存命中率是长轨迹智能体的头号成本指标（缓存工程）。

把状态外化

MemGPT 把上下文当内存、外部存储当磁盘；IterResearch、ReSum、AgentFold 定期重建精简的状态而不是保留全部历史；FS-Researcher 直接把文件系统当工作记忆。

记忆的种类

情节记忆（发生过什么）、语义记忆（事实与偏好）、程序性记忆（怎么做，如 Agent Workflow Memory、Memp）。ACE 把上下文当作不断演化的"剧本"；程序性记忆进一步沉淀就是第 3 章的技能。

最近半年（2026-05 → 2026-10）

橙色为最近半年
  1. 2026-09 → 10记忆要算净价值。Memory Tax 拆解记忆的收益与构建、检索成本，发现成本可能抵消收益；朴素 RAG 比想象中强：在长期对话记忆上，复杂的智能体记忆系统未必胜过朴素检索；预注册实验 选择取代提取显示，选对原始对话轮次往往就够，不必先抽取事实。

  3. 2026-09 → 10长程状态的新表示。显式信念状态代替原始历史来驱动长程决策；FlowState 以执行状态作为记忆；CarryOn 构建面向对象的上下文，避免反复处理冗长交互历史。
  4. 2026-06 → 07"记忆是重建，不是回放"。图记忆与 MemHarness 都主张按当前任务重建相关记忆，而不是检索并原样回放旧片段。
  5. 2026-05 → 10记忆的失效、交接与个性化。STALE 测智能体能否发现自己的记忆已过期；SubtleMemory 针对 OpenClaw 类长期个人智能体；交接税发现编码智能体接手别人产生的轨迹时表现明显下降；先个性化再存储研究长程个性化记忆。
  6. 2026-07 → 10以记忆实现持续学习。以记忆为中心的持续学习让固定权重的智能体靠记忆持续进步；可组合的持续学习机制；智能体上下文管理把记忆与成本当作生命周期和架构问题。

实践建议

  • 系统提示与工具定义放在前缀且保持稳定；历史只追加；监控缓存命中率。
  • 工具输出要截断、分页或只返回摘要；大文件让智能体用 grep、head 按需读取。
  • 长任务让智能体维护进度文件与待办清单，新会话先读它们（长时运行 harness）。
  • 上长期记忆之前，先用"原始对话 + 朴素检索"做基线；记忆要有更新与过期机制。

尚未解决

  • 何时压缩、丢掉什么？如何保证压缩后不丢关键约束？
  • 多用户、多智能体共享记忆的权限与隐私治理（GateMem）；记忆中的谄媚与污染（MemSyco）。

Harness、技能与多智能体

循环之外还需要哪些工程？什么时候该用多个智能体？

Harness 是包住模型的全部程序：系统提示、工具集、权限、上下文策略、子智能体、钩子、验证与重试。同一个模型换一个 harness，成绩可以差很多：StateM 只靠扩展 harness 就在 Terminal-Bench 2.1 上达到 95.3%。技能把可复用的程序性知识打包成按需加载的文件夹；AGENTS.md 一类上下文文件告诉智能体项目约定。多智能体在可以并行拆分的"宽"任务上有效，但 token 开销大、协作容易出错，默认应该从单智能体开始。

为智能体设计接口

SWE-agent 的"智能体—计算机接口"（ACI）表明：给智能体专门设计的查看、搜索、编辑命令，比直接给它人用的 shell 更有效。长时运行任务还需要初始化步骤、进度文件和增量推进（长时运行 harness）。

技能：渐进披露

上下文里只放每个技能的名称和一句描述；任务相关时才读入 SKILL.md，需要时再执行其中的脚本（Agent Skills、开放格式）。思想可追溯到 Voyager 的可执行技能库。

项目上下文文件

AGENTS.md（以及 CLAUDE.md 等）写构建命令、代码风格、测试方法和禁区；Agent READMEs 分析了数千个这类文件的实际内容与演化。

应用：编码与终端智能体

为什么编码是智能体最成熟的应用？怎样把它用好？

代码有天然的验证信号（编译、测试、类型检查）、纯文本的环境和海量训练数据，所以编码智能体最先成熟：从补全，到修 issue，再到在后台并行处理多个任务、连续多日自主开发。SWE-bench Verified 曾是主要标尺；现在评测转向终端任务（Terminal-Bench）、多语言、长程与真实用户请求。终端也在成为通用的动作空间：不少企业自动化用终端智能体比用 GUI 更可靠（终端智能体足以胜任企业自动化）。

定位 → 修改 → 验证

Agentless 证明不用复杂循环，三步流水线也有竞争力；真正的杠杆是验证：能跑的测试既是智能体的反馈，也是 RL 的奖励。

可验证环境是燃料

SWE-Gym、R2E-Gym、SWE-smith、SWE-Universe（百万级）把真实仓库变成训练环境；SWE-RL 与 Skywork-SWE 显示数据与 RL 的扩展收益。

人机分工

推荐流程是"探索 → 计划 → 编码 → 提交"，测试先行，小步提交（Claude Code 最佳实践）。人负责需求、计划审阅和 diff 审阅；智能体负责读代码、改代码、跑测试。

上下文是仓库

大仓库不能整个塞进上下文：让智能体用搜索工具按需探索，或专门训练仓库探索与上下文裁剪（SWE-Pruner）；项目约定写在 AGENTS.md。

应用：计算机、浏览器与手机

没有 API 的时候，智能体怎样操作软件？

GUI 智能体通过截图（或可访问性树、DOM）感知界面，用点击、键入、滚动来行动，因此能操作任何为人设计的软件。两条路线：模块化（规划模型 + 专门的定位模型）与端到端原生 GUI 模型（只看截图直接输出动作）。Claude 计算机使用（2024-10）首次公开了前沿模型的这一能力，随后 Operator、ChatGPT agent、Atlas 把它做进产品。实践上，GUI 慢且脆弱：有 API 或命令行时应优先用它们，最近半年的趋势正是 GUI 与 CLI/API 混合。

感知与定位

瓶颈常在"看懂了却点错了"：把语言描述映射到屏幕坐标。专门的定位模型与数据（OS-ATLAS、GUI-Actor、Phi-Ground、UI 分解合成）是一条主线。浏览器任务可绕开像素，直接用可访问性树（Playwright MCP）。

模块化 vs. 原生

模块化：SeeAct、Agent S、CODA（大脑 + 小脑）。原生：UI-TARS、Aguvis、OpenCUA、GUI-Owl。原生模型更快更统一，模块化更容易换组件。

数据从哪里来

教程回放（AgentTrek）、反向任务合成（OS-Genesis）、人工示范视频（CUA-Suite）、在线 RL（DigiRL、WebRL、ZeroGUI、UI-TARS-2）。

评测

WebArena、Mind2Web、OSWorld、Windows Agent Arena、AndroidLab；最近半年的 OSWorld 2.0 转向真实长程任务。

应用：深度研究与科研智能体

智能体能否替人搜集、综合信息，甚至做研究？

训练智能体：环境、强化学习与自我改进

智能体的能力从哪里来？怎样让它在使用中继续变强？

能力有三个来源。智能体模型：在预训练与中期训练中加入智能体数据，再用轨迹做 SFT、在环境里做 RL（Kimi K2、GLM-4.5、GLM-5）。智能体 RL：多轮、长程、奖励稀疏，难点是信用分配、熵坍缩与 rollout 成本。环境：可执行、可验证的环境是新的"数据"，最近一年的瓶颈从算法转到了环境合成。此外，智能体也可以不改权重地自我改进：积累记忆、技能和更好的 harness（第 2、3 章）；最近半年，"递归自我改进"从口号变成了大量具体工作和专门的评测。

智能体 RL 的特殊之处

工具输出不是模型生成的，通常不计入损失（但 不要掩盖环境发现 SFT 时监督观测反而有益）；几十轮之后才有奖励，需要异步、长轨迹的训练系统（超越十轮）；熵与推理会坍缩（熵调制、RAGEN-2）。

环境就是数据

真实环境贵且难复位，于是合成：程序化生成（EnvScaler）、扩展环境种类（环境扩展、AgentGym-RL）、用 LLM 模拟环境（Agent World Model）、模拟用户（MIMESIS）。

在策略蒸馏（OPD）

学生自己采样，教师对每个 token 打分：比 SFT 更贴合学生的分布，比 RL 的信号更密。最近半年它成为智能体后训练的主力之一，也引来了专门的现实检验。

自我改进的三个层次

上下文与记忆（最便宜、可回滚）→ 技能与 harness（可读、可审计）→ 权重（最持久、最难回滚）。综述见自演化智能体与现代智能体系统的自我改进。

评测：怎样知道它真的有用

公开基准说明了什么、没说明什么？自己的智能体该怎么评？

智能体评测比模型评测难：结果同时取决于模型、harness、环境、随机性和预算。评测分三层：能力基准（编码、GUI、研究、工具对话）、时间视野与经济价值（能独立完成多长、多值钱的工作），以及你自己的应用评测，最后一层最重要。基本原则：报告成本与方差（AI Agents That Matter），用 pass^k 衡量可靠性（τ-bench），防污染，读轨迹而不只看分数。

主要基准

编码：SWE-bench / Verified、Terminal-Bench；GUI：OSWorld、WebArena；研究：GAIA、BrowseComp；工具与对话：τ²-Bench、BFCL；MCP：MCP-Universe、MCP-Bench；ML 研究：MLE-bench、RE-Bench。

时间视野

METR 用"人类专家完成同样任务需要多久"度量智能体：50% 成功率对应的任务时长长期按约 7 个月翻倍。METR 页面在 2026-09 最后一次更新后停止维护，并注明超过 16 小时的测量已不可靠：现有任务集已经不够长。

可靠性与成本

pass@k 看"至少一次成功"，pass^k 看"k 次都成功"，后者才接近上线需要的可靠性。成功率要与成本、延迟一起画成帕累托前沿；HAL 统一了跨 harness、跨模型的报告方式。

怎么判分

能用程序判就用程序（测试、状态检查）；不能时用带评分细则的 LLM 评审，并用人工标注校准；开放任务可以让智能体当评审（Mind2Web 2）。始终保留轨迹供人审阅。

安全与可靠性

怎样才能放心地把权限交给智能体？

智能体把模型的错误变成了真实世界的动作。风险有三类：外部攻击，主要是间接提示注入（网页、文档、邮件、工具输出里夹带的指令）以及工具、技能投毒；模型自身的行为，如越界、欺骗、奖励作弊、压力下的失准；系统可靠性，如不可逆操作、误删、长期部署中的退化。防御的核心是系统设计，不能只靠模型"更听话"：最小权限、沙箱、把数据与控制流分开、关键操作人工确认、可撤销、可审计。

致命三要素

Simon Willison：一个智能体如果同时①能访问私有数据、②会读入不可信内容、③能对外通信，攻击者就可以通过注入让它把数据发出去。三者至少去掉一个。

从设计上隔离

CaMeL 让受信任的模型只根据用户指令生成程序，不可信数据只能作为值流过程序，不能改变控制流；"先计划、后执行"、双模型等模式同理。

权限与沙箱

默认只读；写操作限定目录；网络出口白名单；凭证不进入模型上下文（托管平台可在出口处注入）；不可逆操作逐次确认；所有动作留审计日志。

评测与红队

注入：InjecAgent、AgentDojo、WASP；有害性：AgentHarm；综合：ToolEmu、ASB、OpenAgentSafety；失准：Agentic Misalignment。

实践入门指南：从零做一个能用的智能体

如果今天开始做，按什么顺序、用什么工具、避开哪些坑？

把前面各章的经验压缩成十步。核心思路只有三条：先用最简单的方案，能用工作流就不用智能体；先建评测再迭代，否则无法判断改动是否有效；权限从小开始，智能体的每一项能力都要对应一个护栏。下面的代码用 Anthropic Python SDK 写成，换成其他厂商的 SDK，结构完全相同。

  1. 判断是否真的需要智能体

    问四个问题：步骤能否事先写死？（能 → 工作流）是否需要根据中间结果决定下一步？（是 → 智能体）出错的代价有多大、能否检测？单次任务值不值得几十次模型调用的成本？多数业务问题的正确答案是"单次调用或工作流 + 一两处模型判断"。

  2. 选择搭建层级

    层级适合例子
    直接用产品个人或团队提效，不需要嵌入自己的系统Claude Code、Codex、ChatGPT agent、Antigravity
    托管智能体需要沙箱、长任务、会话管理，但不想自己运维Claude Managed Agents、Gemini 托管智能体
    带 harness 的 SDK想要现成的文件、命令、搜索工具与上下文压缩Claude Agent SDK、OpenAI Agents SDK、ADK
    编排框架有明确状态机、需要持久化与人工介入的业务流程LangGraph、Microsoft Agent Framework、Pydantic AI
    自写循环学习原理、完全掌控、特殊运行环境下面的约 60 行代码；mini-swe-agent 是极简参考

  3. 写一个最小的智能体循环

    一个只读的"代码库问答"智能体：两个工具，只能看 workspace/ 目录，最多 20 步。理解了它，所有框架都只是在这个循环上加功能。

    import pathlib
import anthropic

ROOT = pathlib.Path("workspace").resolve()   # 智能体只能看到这个目录
client = anthropic.Anthropic()               # 从环境变量 ANTHROPIC_API_KEY 读取密钥

TOOLS = [
    {"name": "list_dir",
     "description": "列出 workspace 中某个目录的内容。path 是相对路径，默认 '.'。",
     "input_schema": {"type": "object", "properties": {"path": {"type": "string"}}}},
    {"name": "read_file",
     "description": "读取 workspace 中的文本文件，最多返回 20000 个字符。",
     "input_schema": {"type": "object", "properties": {"path": {"type": "string"}},
                      "required": ["path"]}},
]

def safe_path(rel):
    p = (ROOT / rel).resolve()
    if not p.is_relative_to(ROOT):               # 防止 ../ 逃出工作目录
        raise ValueError(f"{rel} 不在 workspace 内")
    return p

def run_tool(name, args):
    if name == "list_dir":
        d = safe_path(args.get("path", "."))
        return "\n".join(sorted(x.name + ("/" if x.is_dir() else "") for x in d.iterdir()))
    if name == "read_file":
        return safe_path(args["path"]).read_text(errors="replace")[:20000]
    raise ValueError(f"未知工具 {name}")

def run_agent(task, max_steps=20):
    messages = [{"role": "user", "content": task}]
    for _ in range(max_steps):
        resp = client.messages.create(
            model="claude-opus-5-5", max_tokens=16000,
            system="你是代码库助手。先用工具查看文件再回答，并注明依据的文件。",
            tools=TOOLS, messages=messages)
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason == "pause_turn":     # 服务端暂停了长回合：原样续上
            continue
        if resp.stop_reason != "tool_use":       # end_turn 正常结束；max_tokens、refusal 需另行处理
            text = "".join(b.text for b in resp.content if b.type == "text")
            return text, resp.stop_reason
        results = []
        for b in resp.content:
            if b.type != "tool_use":
                continue
            try:
                out, err = run_tool(b.name, b.input), False
            except Exception as e:                # 错误交还给模型，让它自己纠正
                out, err = f"Error: {e}", True
            results.append({"type": "tool_result", "tool_use_id": b.id,
                            "content": out, "is_error": err})
        messages.append({"role": "user", "content": results})   # 所有结果放在同一条消息里
    return "达到步数上限", "max_steps"

answer, why = run_agent("这个项目是做什么的？入口在哪里？")
print(why, answer, sep="\n")

    要点：助手消息原样追加（包括思考块与工具调用块）；一轮里的所有工具结果放进同一条用户消息；工具出错时返回 is_error 而不是中断；用步数上限兜底。不想手写循环时，SDK 的 Tool Runner 可以自动执行这个循环：用 @beta_tool 装饰普通函数，再调用 client.beta.messages.tool_runner(...) 迭代结果。生产环境还要处理 refusal 与 max_tokens、加重试与日志，长输出改用流式。

  4. 把工具设计好

    • 少而精：按"用户要完成的事"设计工具（如 search_orders），而不是把每个底层 API 都暴露出去。
    • 描述写清楚何时用、何时不用、参数格式和返回内容；给出一两个例子。
    • 返回对模型有用的信息：人能读懂的字段而不是内部 ID；结果太长就分页或截断并说明。
    • 错误信息要可操作：说清是哪里错了、该怎么改。
    • 可复用的工具做成 MCP 服务器；写操作的工具单独标注并加确认。参考为智能体编写工具。

  5. 管理上下文与状态

    系统提示与工具定义放在稳定的前缀以命中缓存；长任务让智能体维护 progress.md 与待办清单；工具输出只保留需要的部分；探索性工作交给子智能体，只取回结论；接近上限时压缩旧轮次。详见第 2 章与 Manus 的上下文工程。

  6. 把经验沉淀到 harness、AGENTS.md 与技能

    智能体犯过一次的错，写进 AGENTS.md（项目约定）或做成技能（可复用流程 + 脚本），而不是每次在对话里纠正。技能只在上下文中放名称与一句描述，用到时再加载全文（Agent Skills）。长时任务参考长时运行 harness：先初始化环境与进度文件，再每次推进一小步并提交。

  7. 先建评测，再迭代

    准备 20–50 个真实任务与可检查的完成标准；每个任务跑 3–5 次，记录成功率、成本、延迟；用程序判分优先，LLM 评审需配评分细则并与人工对齐。每次改提示、工具、模型或 harness 都跑回归。追踪每一步（Langfuse、Phoenix、Inspect），每周读轨迹找新的失败模式。

  8. 加上安全护栏

    • 对照致命三要素：私有数据、不可信内容、对外通信，至少去掉一项。
    • 沙箱执行（容器、虚拟机或托管沙箱）；默认只读；网络出口白名单；凭证不进上下文。
    • 不可逆操作（删除、付款、发送、部署）前请人确认；保留撤销手段与审计日志。
    • 只用可信来源的 MCP 服务器与技能；把网页、邮件、文档内容一律当作数据，不当作指令。

  9. 控制成本与延迟

    提示缓存是最大的一笔节省；按步骤难度选模型与推理力度（简单步骤用小模型或低力度）；无依赖的工具调用并行；限制步数与单任务预算；批量离线任务用批处理接口。把"每个成功任务的成本"作为核心指标，而不是每次调用的成本。

  10. 上线与运维

    灰度发布，先只读、再"起草 + 人审"、最后才自动执行；监控成功率、人工接管率、成本与异常动作；固定模型版本，升级前跑评测；收集用户修改与差评作为新的评测与改进数据；长期运行的智能体定期复查记忆与技能，防止"衰老"（智能体也会衰老）。

四周学习路径

  1. 第 1 周 · 用：每天用一个编码智能体（Claude Code、Codex 或开源的 OpenHands、Aider）完成真实任务；读 Building effective agents 与 A practical guide to building agents。
  2. 第 2 周 · 写：手写上面的循环，再加一个写文件工具与确认机制；把一个工具做成 MCP 服务器；读 ReAct、SWE-agent、工具设计。
  3. 第 3 周 · 评：为自己的场景做 20 个任务的评测集，比较两种模型或两种提示的成功率与成本；读 AI Agents That Matter、τ-bench。
  4. 第 4 周 · 稳：加上下文管理、AGENTS.md 与一个技能；做一次提示注入自测；读 上下文工程、致命三要素、CaMeL。

常见错误

  • 一上来就做多智能体：先把单智能体做到可靠。
  • 工具太多、描述太短，模型选错工具或乱填参数。
  • 没有评测，凭几个例子的"感觉"改提示，越改越差。
  • 把整份文档、整个网页塞进上下文，成本高且效果差。
  • 给了写权限却没有沙箱、确认和撤销手段。
  • 只看成功率不看成本；只看最终结果不看轨迹。
  • 把业务规则只写在提示里，而不是写成工具中的校验。
