The Journey of DeepSeek

2023 年 11 月，DeepSeek 的第一个通用大模型是一个照着 LLaMA 搭的 67B 稠密 Transformer。三年后，旗舰变成了总参数 1.6T、每个 token 只激活 49B、能读百万 token 的 V4-Pro，以及每个 token 只缓存 890 字节、原生多模态的 V4.1-Flash。本文按时间顺序，把中间的每一步迭代走一遍。

每一步都按同样的顺序写：上一步卡在哪里；这一步改了什么（公式、张量形状、超参数）；换来了什么；配方里因此多了什么、少了什么。需要的背景是 Transformer、RoPE、SwiGLU、MoE 和 PPO 的基本概念。

整条路线可以压成一句话：每一步都在压同一个成本，也就是每个 token 要动用多少参数、读写多少字节；省下来的预算再换成更大的模型、更长的上下文和更多的强化学习。具体是三条线交替推进：

  • 架构。稠密 → 细粒度 MoE（参数和计算脱钩）→ MLA（每条 KV 变小）→ DSA（每次只算 top-k 条）→ CSA / HCA（沿序列把 KV 压短）→ CSA2 + CED（多层共用一份 KV）。
  • 后训练。SFT + DPO → GRPO（去掉价值网络）→ 只给结果奖励的纯 RL（长推理）→ 规模化 RL 与合成智能体环境 → 分领域专家加在策略蒸馏 → 算法不再变，收益来自数据和环境。
  • 系统。FP8 训练、DualPipe、专家并行通信、前缀缓存落盘、FP4。每一代的架构改动都和 kernel、部署方式一起设计。

第 0 步 · 2023-11 · DeepSeek LLM

起点：照着 LLaMA 搭一个稠密模型，先把缩放律摸清楚

DeepSeek 最早发布的是 2023-11 初的 DeepSeek Coder（1.3B–33B，2T token，其中 87% 是代码，按仓库依赖关系排列文件，并训练 FIM 补全），月底发布了通用模型 DeepSeek LLM 7B 和 67B。

DeepSeek LLM 的 block 基本照搬 LLaMA：Pre-Norm 加 RMSNorm，FFN 用 SwiGLU（中间维 83d\tfrac83 d38​d），位置编码用 RoPE。67B 用 GQA，64 个 query 头共享 8 组 KV 头。宏观上有一处不同：为了便于切分流水线，也为了效果，加参数时加的是深度而不是 FFN 宽度，7B 是 30 层，67B 是 95 层（宽 8192）LLM §2.2。数据是 2T token 中英文，分词器是 byte-level BPE，训练用词表 102,400。对齐用约 150 万条中英文 SFT 数据，再做一轮 DPO。

卡住的地方

稠密模型的每个 token 都要动用全部 67B 参数，训练和推理的计算量都与参数量成正比。推理时还有 KV 缓存：

第 1 步 · 2024-01 · DeepSeekMoE

让参数和计算脱钩：把专家切细，再拿出几个当共享专家

上一步留下的问题

稠密模型的计算量随参数量线性增长。MoE 是现成的答案：把 FFN 换成 NNN 个专家，每个 token 只走其中 KKK 个。但当时主流的 GShard、Switch、Mixtral 式 MoE（16 选 2、8 选 2）有两个毛病DeepSeekMoE §1：知识混杂，专家太少，每个专家被迫同时装下许多不相干的知识；知识冗余，通用知识（语法、常见搭配）每个专家都要各学一遍。

改了什么

  1. 细粒度切分。把每个专家的 FFN 中间维缩小为 1/m1/m1/m，专家数变成 mNmNmN，每 token 激活 mKmKmK 个。总参数和每 token 计算量都不变，组合方式却多出几个数量级：16 个专家选 2 个只有 120 种组合；每个切成 4 份后 64 选 8，有 4,426,165,368 种。每个专家因此可以只负责一类更窄的模式。
  2. 共享专家隔离。拿出 KsK_sKs​ 个专家让每个 token 都必经，专门承载通用知识；路由专家相应少激活 KsK_sKs​ 个，总计算量不变。

负载均衡靠两项辅助损失：专家级损失防止路由坍缩到少数几个专家，设备级损失让各张卡的计算量均衡。

DeepSeekMoE 16B 的配置：28 层，宽 2048；除第 1 层外，FFN 全部换成 MoE；每层 2 个共享专家 + 64 个路由专家，每个专家是标准 FFN 的 1/4 大小；每个 token 走 2 个共享专家和 6 个路由专家。总参数 16.4B，激活约 2.8BDeepSeekMoE §5。

换来什么

  • 2B 规模：与 GShard 2.9B 持平，后者的专家参数和计算量都是它的 1.5 倍；并且接近“同总参数稠密模型”这个 MoE 的理论上限。
  • 16B（2T token）：用约 40% 的计算量，达到 LLaMA2 7B 和 DeepSeek LLM 7B 的水平。
  • 145B 的初步实验：用 28.5%（可能低至 18.2%）的计算量，达到 DeepSeek LLM 67B 的水平。

“细粒度路由专家 + 共享专家”这个结构此后再没有换过。后面各代改的只是数量（V2 选 160 中的 6 个，V3 选 256 中的 8 个，V4-Pro 选 384 中的 6 个）、打分函数和均衡方式。

第 2 步 · 2024-02 · DeepSeekMath

后训练的第一个关键零件：去掉价值网络的 GRPO

上一步留下的问题

开源模型在竞赛数学上远远落后 GPT-4。缺两样东西：足量的数学预训练数据，以及一个在大模型上负担得起的 RL 算法。PPO 需要一个和策略模型差不多大的价值网络，显存和计算都要翻倍。

数据：从 Common Crawl 里把数学网页捞出来

以 OpenWebMath 为种子训练一个 fastText 分类器，从去重后的 Common Crawl 里召回数学网页。第一轮召回的多样性不够，于是按域名统计：一个域名下超过 10% 的网页被召回，就认定它与数学相关（如 mathoverflow.net），人工标出其中的数学 URL 路径，把还没召回的网页补进种子集，重训分类器。迭代 4 轮，得到 3550 万个网页、120B tokenDeepSeekMath §2。模型从 DeepSeek-Coder-Base-v1.5 7B 出发继续训练 500B token，其中 56% 是这份数学语料。两个副产品结论：先在代码上训练有助于数学推理；arXiv 论文对提升数学推理几乎没有帮助。

一个后来很重要的观察

论文把 SFT、拒绝采样微调、DPO、PPO、GRPO 统一写成“数据来源 × 奖励函数 × 梯度系数”来比较，并发现 RL 提升的是 Maj@K（多数投票），而不是 Pass@K。也就是说，RL 让模型更稳定地给出它本来就能给出的正确答案，并没有教会它新的东西DeepSeekMath §5.2。这个结论是在 7B 模型、最长 1024 token 的设定下得出的；第 5 步的 R1 会在强得多的基座、长得多的输出上重新检验它。

第 3 步 · 2024-05 · DeepSeek-V2

第一次组装：MoE + MLA，训练成本省 42.5%，KV 缓存少 93.3%

上一步留下的问题

DeepSeekMoE 解决了计算量，推理成本的另一半还没动：67B 每 token 389 KB 的 KV 缓存决定了一张卡能同时服务多少请求，也让 128K 上下文几乎没法部署。MQA、GQA 靠减少 KV 头数来省缓存，但会损失效果。

第 5 步 · 2025-01 · DeepSeek-R1

不教模型怎么想，只奖励它答对：纯 RL 长出长思维链

上一步留下的问题

2024-09 的 OpenAI o1 表明，让模型先长时间“思考”可以大幅提升推理能力，但没有公开怎么做到的。常见的猜测是需要过程奖励模型或蒙特卡洛树搜索。而 DeepSeekMath 的结论是 RL 只是让已有能力更稳定（第 2 步）。问题是：在一个足够强的基座上，只给结果奖励的 RL 能不能把推理能力本身练出来？

5.1 R1-Zero：直接在 V3-Base 上做 RL

不经过任何 SFT。奖励只有两项，权重相同：规则判定的答案正确性（数学看最终答案，代码跑测试），以及格式（推理写在 <think>…</think> 里）。推理任务刻意不用神经奖励模型，无论是结果式还是过程式，因为大规模 RL 中它们容易被投机利用（reward hacking），重训它们也很贵R1 §2。

超参数：学习率 3e-6，KL 系数 0.001，采样温度 1；每题采样 16 个回答，最大长度在第 8.2K 步之前为 32,768，之后为 65,536；每步 32 道题，batch 512；每次 rollout 生成 8192 个回答，随机分成 16 个 mini-batch，只训一个内层 epoch；每 400 步把参考模型更新为最新策略；共 10,400 步。

结果：AIME 2024 的 pass@1 从 15.6% 升到 77.9%，自洽投票后 86.7%。没有人教，模型自己学会了把思维链越写越长、自我检查和回溯，中间版本还出现了“wait, wait… that's an aha moment”这样的自我纠正。响应长度和准确率都在第 8.2K 步附近跳升。这回答了第 2 步留下的问题：在足够强的基座和足够长的输出预算下，RL 带来的不只是稳定性。

5.2 R1：把可读性补回来

R1-Zero 的思维链可读性差、中英混杂。R1 改成多阶段流水线：

  1. 几千条长思维链冷启动数据做 SFT；
  2. 推理 RL，加入语言一致性奖励，即思维链中目标语言词所占的比例；
  3. 拒绝采样得到约 60 万条推理数据，加上约 20 万条非推理数据，共约 80 万条，再做 SFT；
  4. 面向全场景的 RL：推理题用规则奖励，通用题用有用性和无害性奖励模型。

同样这 80 万条数据，在 Qwen、Llama 的 1.5B–70B 基座上训 2–3 个 epoch，就是同时发布的六个蒸馏小模型。

8.7 系统：为新架构重写的部分

  • 按“波次”调度的专家并行。把专家分成若干波次，一波专家收齐 token 就开始算；稳态下本波计算、下一波传输、上一波回传同时进行。以 MegaMoE 之名开源在 DeepGEMM 中，一般推理负载提速 1.50–1.73 倍。报告还给出一个硬件结论：V4-Pro 每个 token-专家对需要 6hd6hd6hd FLOPs、通信 3h3h3h 字节，所以只要算力与带宽之比 ≤2d=6144\le 2d = 6144≤2d=6144 FLOPs/Byte，通信就能被完全掩盖V4 §3.1。
  • kernel 与确定性。几百个细碎算子换成 TileLang 写的融合 kernel；预训练、后训练、推理三条管线逐比特对齐（不用 split-KV、基本不用 split-k、稀疏注意力反向不用 atomicAdd）。
  • Muon 与 ZeRO 的冲突。Muon 需要完整矩阵，ZeRO 会把它切碎；V4 用背包算法把整块矩阵分给各 rank。
  • 异构 KV 缓存。一层可能是 CSA、HCA 或纯滑窗，PagedAttention 的假设不再成立。V4 把缓存分成每请求固定大小的“状态缓存”（滑窗 entry 和还凑不满一个压缩块的尾部）与按块管理的压缩 KV（每块覆盖 128 个原始 token）。前缀缓存落盘时压缩 KV 全存；滑窗 KV 体积约为压缩 KV 的 8 倍，提供全存、隔段存检查点、完全不存三种策略V4 §3.5。

# X: [T, 4, d]，每个 token 有 4 条残差流（mHC）
def block(X, ids, layer):
    for sub in (attention, moe):                 # 注意力、FFN 各配一套 mHC 系数
        A, B, C = mhc_coeffs(X)                  # A:[T,4]  B:[T,4,4] 双随机  C:[T,4]
        x = rmsnorm(einsum("th,thd->td", A, X))  # 4 条流加权合成 1 条，送入子层
        y = sub(x, ids, layer)
        X = einsum("thk,tkd->thd", B, X) + C[..., None] * y[:, None, :]
    return X

def attention(x, layer):                         # layer.m ∈ {0: 纯滑窗, 4: CSA, 128: HCA}
    cq = rmsnorm(x @ W_dq)                       # query 的低秩 latent（第 3 步），indexer 也用它
    q  = rms(cq @ W_uq).view(T, n_h, 512); rope(q[..., -64:], pos)
    kv = rmsnorm(x @ W_kv); rope(kv[..., -64:], pos)
    keys = last(kv, 128)                         # 滑窗：最近 128 条未压缩 entry
    if layer.m:
        comp = compressor(x, layer.m)            # 每 m 个 token 合成 1 条 entry
        idx = topk(indexer(x, cq), k) if layer.m == 4 else all_visible(comp)
        keys = concat(keys, comp[idx])
    p = softmax_with_sink(q @ keys.T / sqrt(512))   # 所有头共享同一组 entry（MQA）
    o = p @ keys                                 # value 就是 key 本身
    rope(o[..., -64:], -pos)                     # 反向旋转，去掉绝对位置
    return grouped_out_proj(o)                   # n_h·512 → g×1024 → d

def moe(x, ids, layer):
    s = sqrt(softplus(x @ E.T))                  # [T, N_r] 亲和度
    top = HASH[ids] if layer < 3 else topk(s + b, 6)  # 偏置 b 只影响“选谁”（第 4 步）
    w = s.gather(top); w = rho * w / w.sum(-1)
    return shared(x) + sum(w[k] * expert[top[k]](x) for k in range(6))

9.1 CED：下半个网络给上半个网络算好全局 KV

受 YOCO 启发，把 40 层分成下面 20 层的“因果编码器”和上面 20 层的“解码器”。解码器各层的全局 KV 不由本层隐藏状态计算，而是用各层自己的投影矩阵，从编码器最后一层的输出 HL/2H_{L/2}HL/2​ 直接投影V4.1 §2.2：

Cl=HL/2WlKV,Zl=HL/2WlZ,l>L/2.C_l = H_{L/2}W^{KV}_l,\qquad Z_l = H_{L/2}W^{Z}_l,\qquad l > L/2 .Cl​=HL/2​WlKV​,Zl​=HL/2​WlZ​,l>L/2.

prefill 一段提示词时，只需跑完编码器就能拿到解码器全部的全局 KV：prefill 激活 8B 参数，decode 激活 16B。滑窗 KV 仍由每层自己的隐藏状态逐层计算，以保留局部计算的深度；代价是解码器的滑窗需要“回放”（9.5）。

9.2 CSA2：相邻层共用主 KV 和 top-k 索引

每层静态指定为三种模式之一，三者都计算本层自己的 query 和滑窗 KV，区别在于主 KV、索引键和 top-k 从哪里来V4.1 §2.3.1：Full 全部自己算；Reindex 复用最近一个 Full 层的主 KV 和索引键，但用本层的索引 query 重新选 top-k；Reuse 主 KV 和 top-k 都直接复用。压缩器同时简化：去掉重叠窗口和位置偏置，索引键改从主 KV 投影，不再单开一条压缩通路。HCA 不再使用。

9.6 部署：滑窗 KV 不再落盘

线上数据显示，滑窗 KV 只在一次活跃会话的几分钟内会被复用，而全局 KV 的复用有很长的尾巴。V4.1 把全局 KV 留在 SSD 上保证至少存活 72 小时，滑窗 KV 只放进一个由各机器 10% 主机内存组成、TTL 几分钟的内存池V4.1 §3.2。滑窗缺失时做有界回放：编码器只回放前缀最后 nwinn_{\text{win}}nwin​ 个 token，得到近似的滑窗状态；解码器每次 prefill 只把提示词最后 128 个 token 的编码器输出送进解码层，后训练时也模拟这种回放，让模型提前适应。持久化缓存因此缩小到 V4 的约 1/8。

9.7 后训练：算法不变

报告明确说这一版没有引入新的后训练算法，仍是 SFT → RL → OPD，全部变化在数据管线上V4.1 §1 · §5.1：任务形式化为（问题，环境，验证系统）三元组，由多智能体协作自动构建代码环境（判断能否构建、写测试、多个智能体尝试求解、质检、修复）；在多种外部脚手架上联合做 RL；推理强度变成系统提示里 1–100 的连续值 bbb，长度惩罚随 bbb 指数衰减，线上 max、high、low 三档对应 b=100,75,50b = 100, 75, 50b=100,75,50；RL 改为与训练分时共用 GPU 的异步模式；最终 OPD 的教师超过 40 个。

三个规律

  • 新零件先在旧模型上试，再进下一代旗舰。GRPO 先在 7B 数学模型上验证（第 2 步），才进 V2；无辅助损失均衡先是一篇 3B 规模的论文，才进 V3；稀疏注意力先是研究原型 NSA，再以 V3.2-Exp 的形式“只换注意力、其余配置对齐”地在已有模型上验证，最后才在 V4 里从预训练开始使用；mHC 和 Engram 各自先发论文；视觉先以 V4-Flash-Vision-Exp 试水，再在 V4.1 中做成原生多模态。
  • 证明可继承的零件会一直留下。细粒度专家加共享专家、GRPO、FP8 训练、MLA 的“所有头共享一条低秩 entry + 部分 RoPE”，从首次引入一直用到现在，只是参数在变。被替换的往往是为当时约束打的补丁：丢 token、设备级均衡损失、节点数限制、阶梯学习率、MTP。
  • 后训练从算法创新转向工程和数据。GRPO 和 R1-Zero 是算法上的突破；V3.2 的四项修正是让算法在规模上稳住；V4 的 OPD 主要难在工程（全词表 KL、教师调度、可抢占 rollout）；到 V4.1，报告直接说算法没有变化，收益全部来自数据和环境。

边界

公开材料没有给的部分

结构部分可以完全复现：权重、config.json 和参考推理代码都已公开，本文的形状和字节数也都能据此验算。真正卡住复现的是下面这些：

  • 数据。没有配比、过滤阈值和质量模型，也没有 V4.1 那套“缩放阶梯”的具体设计。
  • 算力。V2、V3、R1 公布了卡时；V3.2 之后的报告没有公布卡时、集群规模和硬件型号。
  • 后训练超参数。V4 各专家的 GRPO 超参数只写了“与先前工作基本一致”；长度惩罚的系数、离策略屏蔽的阈值 δ\deltaδ、各领域的 KL 强度都没有数值。
  • 后训练资产。专家和教师的完整名单、rubric 数据、SFT 数据规模、各领域的环境数量（V3.2 给过，V4、V4.1 没给）。
  • 稳定性机制的细节。Anticipatory Routing 的 Δt\Delta tΔt 和 spike 检测规则；V4 的 indexer 预热步数；哈希路由表的生成方式（表本身随权重发布）。
  • 评测。与闭源模型对比的分数几乎都是自测的，脚手架、推理预算和采样参数影响很大：V4.1 报告了同一个模型在 8 种智能体脚手架下的 DeepSWE 分数，从 65.5 到 74.2 不等。

建议的阅读顺序。按本文的顺序读一手材料：DeepSeekMoE 和 DeepSeekMath 各读方法一节；V2 §2（MLA、设备受限路由）；V3 §2–3（无辅助损失均衡、MTP、FP8、DualPipe）；R1 §2；V3.2 §2–3；V4 §2–5；V4.1 §2–5。读每份报告时都把 Hugging Face 上对应的 config.json 和 inference/model.py 开在旁边，那里有报告省略的细节。
