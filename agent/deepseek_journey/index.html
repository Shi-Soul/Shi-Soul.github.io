DeepSeek 的旗舰模型由四样东西叠成：

  1. 稀疏 FFN。DeepSeekMoE：每层 1 个共享专家 + 384 个细粒度路由专家，每个 token 只激活其中 6 个（V4-Pro）。
  2. 压缩加稀疏的注意力。每个位置只缓存一条 512 维向量，它同时充当 key 和 value；再沿序列方向把 4 个或 128 个 token 合并成一条；压缩率为 4 的层还要用一个轻量打分器（indexer）只挑出 top-1024 条参与注意力。V4-Pro 在长上下文下每 token 的全局 KV 约 5 KB，约为同层数 GQA-8 基线的 2%。
  3. 4 路宽的残差流（mHC）。层与层之间的残差混合矩阵用 Sinkhorn 迭代投影成双随机矩阵，保证信号不会被放大。
  4. 训练配方。Muon 优化器 + FP8 混合精度，33T token，序列长度从 4K 分段扩到 1M。后训练分两步：先按领域分别训练专家模型（SFT + GRPO），再用多教师、全词表的在策略蒸馏把它们合成一个模型；后训练期间同时做 FP4 量化感知训练，直接产出部署用的权重。

“旗舰”指哪个。截至 2026-11，参数最多的是 V4-Pro（2026-04，1.6T 总参数 / 49B 激活）；架构最新的是 V4.1-Flash（2026-09，552B 主干 + 196B Engram 记忆参数，原生多模态），它在多数智能体评测上已经超过 V4-Pro。本文以 V4 为主体完整搭一遍，V4.1 的全部改动单独放在 §08。V2、V3、V3.2 只在“V4 从哪里继承了什么”时出现。

02 · 前向

一个 V4 block 到底算了什么

下面的伪代码按参考推理代码 inference/model.py 整理，只删去了并行和量化细节。每一行在后文都有对应的小节。

# X: [T, 4, d]，每个 token 有 4 条残差流（mHC，§06）
def block(X, ids, layer):
    for sub in (attention, moe):                 # 注意力、FFN 各配一套 mHC 系数
        A, B, C = mhc_coeffs(X)                  # A:[T,4]  B:[T,4,4] 双随机  C:[T,4]
        x = rmsnorm(einsum("th,thd->td", A, X))  # 4 条流加权合成 1 条，送入子层
        y = sub(x, ids, layer)
        X = einsum("thk,tkd->thd", B, X) + C[..., None] * y[:, None, :]
    return X

def attention(x, layer):                         # layer.m ∈ {0: 纯滑窗, 4: CSA, 128: HCA}
    cq = rmsnorm(x @ W_dq)                       # [T, d_c]，query 的低秩 latent，indexer 也用它
    q  = rms(cq @ W_uq).view(T, n_h, 512)        # 每头再做一次无参数 RMS 归一化
    rope(q[..., -64:], pos)
    kv = rmsnorm(x @ W_kv); rope(kv[..., -64:], pos)   # 每个 token 一条 512 维 entry，只供滑窗用
    keys = last(kv, 128)                         # 滑窗：最近 128 条未压缩 entry
    if layer.m:
        comp = compressor(x, layer.m)            # 每 m 个 token 合成 1 条 entry（§04）
        if layer.m == 4:                         # CSA：indexer 只挑 top-k 条
            idx = topk(indexer(x, cq), k)
        else:                                    # HCA：压缩后已经很短，全看
            idx = all_visible(comp)
        keys = concat(keys, comp[idx])
    p = softmax_with_sink(q @ keys.T / sqrt(512))   # 所有头共享同一组 entry（MQA）
    o = p @ keys                                 # value 就是 key 本身
    rope(o[..., -64:], -pos)                     # 反向旋转，去掉输出里的绝对位置
    return grouped_out_proj(o)                   # n_h·512 → g×1024 → d

def moe(x, ids, layer):
    s = sqrt(softplus(x @ E.T))                  # [T, N_r] 亲和度
    top = HASH[ids] if layer < 3 else topk(s + b, 6)  # 偏置 b 只影响“选谁”
    w = s.gather(top); w = rho * w / w.sum(-1)
    return shared(x) + sum(w[k] * expert[top[k]](x) for k in range(6))

整个模型是：词嵌入复制成 4 条流 → 61 个 block → 用一组按输入计算的 sigmoid 权重把 4 条流加权合成 1 条 → RMSNorm → 输出头。另外挂一个 MTP 模块，用来多预测一个 token（§07）。

03 · KV 缓存账本

为什么几乎每个设计都绕着“每 token 多少字节”转

自回归解码每生成一个 token，都要把整个上下文的 KV 缓存从显存读一遍，计算量却很小，所以解码速度主要受显存带宽限制。上下文到了百万级，KV 缓存既决定一张卡能同时服务多少请求，也决定“前缀缓存”（把算过的 KV 存到 SSD，下次同前缀的请求直接读）要占多少磁盘、传输多慢。智能体负载的输入远多于输出，前缀命中又很频繁，这个数字因此直接决定成本。DeepSeek 每一代报告都会报这个数，V4.1 报告的首页图就是它。

定义：全局 KV / token = 所有层为每个位置在长上下文中常驻保存的字节数之和。滑动窗口的那部分不随上下文增长，单独计。

04 · 注意力

从 MLA 到 CSA / HCA：沿三个维度压缩

MLA（V2, 2024-05）→NSA（2025-02，研究原型）→DSA（V3.2-Exp, 2025-09）→CSA + HCA（V4, 2026-04）→CSA2 + CED + FP4 KV（V4.1, 2026-09）

KV 缓存可以从三个相乘的维度压：每条 entry 的大小（MQA/GQA 减少 KV 头数，MLA 改为所有头共享一个低秩 latent），序列长度（把 mmm 个 token 合成一条 entry），以及层数（让多层共享同一份缓存）V4.1 §2.3。DeepSeek 依次做了这三件事：V2 压 entry 大小，V3.2 的 DSA 在不减少缓存的前提下减少每次参与计算的 entry 数，V4 压序列长度，V4.1 压层数。

4.2 DSA：缓存不变，只算 top-k

MLA 减少的是每条 entry 的大小，但每个 query 仍要和全部历史位置做注意力，计算量是 O(L2)O(L^2)O(L2)。DSA 在主注意力前面加了一个很便宜的打分器 lightning indexer，为每个 query 挑出 top-k 个历史位置，主注意力只在这些位置上计算V3.2 §2.1：

Cl=HL/2WlKV,Zl=HL/2WlZ,l>L/2.C_l = H_{L/2}W^{KV}_l,\qquad Z_l = H_{L/2}W^{Z}_l,\qquad l > L/2 .Cl​=HL/2​WlKV​,Zl​=HL/2​WlZ​,l>L/2.

8.2 CSA2：三种静态模式，跨层共享 KV 和 top-k 索引

每层被静态指定为三种模式之一。三种模式都会计算本层自己的主 query 和滑窗 KV，区别在于主 KV、索引键和 top-k 索引从哪里来V4.1 §2.3.1：

  • Full：自己计算主 KV，用它投影出索引键，再自己跑 indexer 得到 top-k。
  • Reindex：复用最近一个 Full 层的主 KV 和索引键，用本层的索引 query 重新打分、重新选 top-k。
  • Reuse：主 KV 和 top-k 索引都直接复用，不跑 indexer。

另外两处简化：压缩器去掉了 CSA 的重叠窗口和绝对位置偏置；索引键改为从主 KV 投影得到，不再单独开一条压缩通路。V4.1 不再使用 HCA，全部是 CSA2。具体排布见 config（kv_source_layer_ids 与 index_source_layer_ids）：

8.3 分层稀疏 indexer

跨层复用减少了 indexer 的调用次数，但剩下的每次调用仍要扫描全部可见上下文。在解码器里，第一个 Full 层（第 20 层）先在全部位置上打分，选出自己的 top-512；同时把每 8 个位置分成一块，以块内最高分作为块分数，选出 2048 块，共 16,384 个候选位置。之后的 Reindex 层只在这个候选池里打分V4.1 §2.3.2。这样，深层 indexer 的单 query 开销与上下文长度无关。这一机制在后训练阶段引入，训练和推理时采用完全相同的候选限制。

DSpark。DSpark 是投机解码的草稿模块：3 个 Transformer block，滑窗 128；一次前向并行给出 5 个草稿位置的基础 logits，再用一个轻量 Markov 头建模草稿 token 之间的依赖；置信度头预测每个位置的条件接受概率，调度器结合引擎的实测吞吐曲线，为每个请求动态决定验证长度。它在预训练结束后单独训练（冻结主干），后训练期间继续跟着更新，但梯度不回传主干，因此 RL 和 OPD 的 rollout 也能用它加速V4.1 §2.4.3。

8.7 多模态

9.2 FP8 混合精度训练（V3 起）

V3 是最早公开的超大规模 FP8 训练配方之一，V4 沿用V3 §3.3：

  • 细粒度 scale。激活按 1×128 的 tile 量化，权重按 128×128 的块量化，scale 在线计算，不用 delayed scaling。
  • 提升累加精度。H800 Tensor Core 的 FP8 累加只有约 14 位有效精度。V3 每累加 NC=128N_C = 128NC​=128 个元素，就把部分和拷到 CUDA Core 上的 FP32 寄存器中累加。

发布的权重本身就是 FP8（E4M3，128×128 块，scale 格式 UE8M0），V4 的专家权重是 FP4。

9.3 FP4 量化感知训练（V4 后训练）

后训练阶段对两处做 MXFP4 的 QAT：MoE 专家权重（显存占用的大头），以及 CSA indexer 的 QK 通路V4 §5.2.1。专家权重的做法是：FP32 主权重先量化为 FP4，再反量化为 FP8 参与计算。由于 E4M3 比 E2M1 多 2 个指数位，只要一个 128×128 的 FP8 块内各个 1×32 的 FP4 子块 scale 的最大最小比不超过某个阈值，这次反量化就是无损的；实测权重满足这个条件。于是整个 QAT 可以直接复用 FP8 训练框架，反向传播相当于对量化操作用直通估计器（STE）。RL 采样和推理时直接用真正的 FP4 权重，保证采样时的行为与线上部署一致。

9.4 两个防 loss spike 的技巧

万亿参数 MoE 训练中出现过明显的不稳定。DeepSeek 发现 loss spike 总是与 MoE 层里的离群值相伴，而路由机制会放大这些离群值。报告坦白说两种方法为什么有效还没有完整的理论解释V4 §4.2.3：

  • Anticipatory Routing。第 ttt 步用当前参数 θt\theta_tθt​ 计算特征，但路由索引用历史参数 θt−Δt\theta_{t-\Delta t}θt−Δt​ 计算。实现上，在第 t−Δtt-\Delta tt−Δt 步就提前取出第 ttt 步的数据，算好路由并缓存。这需要多一次前向，开销约 20%，因此只在自动检测到 spike 时才短暂回滚并启用，过一段时间再切回正常训练，总体开销可以忽略。
  • SwiGLU 截断。见 §05，V4-Flash 和 V4-Pro 整个训练过程都开着。

10 · 训练系统

并行策略、通信重叠与确定性

10.1 V3 的底座

V3 在 2048 张 H800 上训练（每节点 8 卡，节点内 NVLink，节点间 InfiniBand），使用自研框架 HAI-LLM：16 路流水线并行、跨 8 个节点的 64 路专家并行、ZeRO-1 数据并行，不用张量并行V3 §3.1–3.2。

  • DualPipe。跨节点专家并行让计算与通信之比接近 1:1。DualPipe 把每个 chunk 拆成注意力、all-to-all 分发、MLP、all-to-all 合并四段，反向再按 ZeroBubble 的做法拆成“对输入”和“对权重”两部分，让一对前向和反向 chunk 的计算与通信互相掩盖；同时从流水线两端双向送入微批次，减少流水线气泡。
  • all-to-all 内核。先走 IB 发到目标节点上同号的 GPU，再经 NVLink 转发给目标专家所在的卡。只用 20 个 SM 就能跑满 IB 和 NVLink 带宽。
  • 省显存。反向时重算 RMSNorm 和 MLA 的升维投影；参数的 EMA 放在 CPU 上；MTP 模块与主模型的嵌入和输出头放在同一个流水线 rank 上，物理共享。

V3 公布的成本：预训练 2.664M H800 卡时，上下文扩展 119K，后训练 5K，合计 2.788M 卡时。按每卡时 2 美元计约 557.6 万美元，只包括最终那一次训练，不含前期研究和消融。V4、V4.1 的报告没有公布算力和硬件规模。

10.2 V4 新增的系统工作

  • 按“波次”调度的细粒度专家并行。一个 MoE 层由两段通信（dispatch、combine）和两段计算（两个线性层）组成。实测单层内通信总时间小于计算总时间，所以把专家分成若干波次：一个波次的专家收齐 token 就立即开始计算；稳态下，本波次的计算、下一波次的 token 传输、已完成专家的结果回传同时进行。这个融合 kernel 以 MegaMoE 之名开源在 DeepGEMM 中，一般推理负载提速 1.50–1.73 倍，RL rollout 这类小 batch 长尾场景最高 1.96 倍V4 §3.1。
  • 给硬件设计的一个量化结论。能否完全掩盖通信，取决于算力与带宽之比，而不只是带宽本身。V4-Pro 每个 token-专家对需要 6hd6hd6hd FLOPs，通信只有 3h3h3h 字节（FP8 分发 + BF16 合并），所以条件是 C/B≤2d=6144C/B \le 2d = 6144C/B≤2d=6144 FLOPs/Byte：每 1 GB/s 的互联带宽足以掩盖 6.1 TFLOP/s 算力的通信，超过这个点再加带宽，收益递减。
  • TileLang。架构复杂到会产生几百个细碎的 ATen 算子，绝大多数被换成了 TileLang 写的融合 kernel。为降低 CPU 端的调用开销，TileLang 把 host 端的检查逻辑也生成成代码，单次调用的校验开销从几十到几百微秒降到 1 微秒以下；用 Z3 SMT 求解器做整数分析；默认关闭 fast-math，并支持与 CUDA 参考实现逐比特对齐。
  • batch 不变且确定性的 kernel。目标是预训练、后训练和推理三条管线逐比特对齐。解码注意力不用 split-KV，改为双 kernel：一个用单 SM 算完整序列，另一个用多 SM 处理最后不满的一波，二者的累加顺序完全相同。矩阵乘全部换成 DeepGEMM，并且基本不用 split-k。稀疏注意力的反向不用 atomicAdd，改为每个 SM 一块累加缓冲，最后统一做确定性求和。MoE 反向在 rank 内预处理 token 顺序。
  • Muon 与 ZeRO 的冲突。Muon 需要完整的梯度矩阵，而 ZeRO 会把矩阵切碎。V4 对稠密参数限制 ZeRO 的并行度，用背包算法把整块矩阵分给各个 rank（每个 rank 不超过 5 个矩阵，padding 开销低于 10%）；MoE 参数按专家整块分配。MoE 梯度用随机舍入压成 BF16 再同步，并用“all-to-all + 本地 FP32 求和”代替 reduce-scatter，避免低精度累加误差V4 §3.4.1。
  • 压缩注意力下的上下文并行。压缩需要连续 mmm 个 token，可能跨越两个 rank 的边界，而且打包后各序列的压缩长度不同。做法分两段：第一段，每个 rank 把自己最后 mmm 个未压缩 entry 发给下一个 rank，由后者完成跨界压缩；第二段，all-gather 所有压缩 entry，再用一个融合的 select-and-pad 算子整理成完整序列V4 §3.4.3。
  • 张量级激活重算。基于 TorchFX 追踪整张计算图。开发者只需标注哪些张量要重算，框架自动找出重算所需的最小子图，插到对应的反向计算之前；重算结果直接复用原张量的存储指针，没有额外拷贝。

10.3 V4.1 新增

  • CSA2 跨流水线阶段共享。共享同一份主 KV 或 top-k 的层可能分在不同的流水线阶段。做法是在每个使用方阶段放一个“影子 indexer”副本，参数只有一个逻辑所有者；需要跨阶段传递的中间量加进点对点通信的 payload；按微批次管理共享状态的生命周期V4.1 §3.1.2。
  • Engram 并行。Engram 表按行切分到专门的进程组上，优化器状态再在副本间切分。查表索引只取决于输入，所以每步开始前就对整个本地 batch 发起预取；梯度在主干反向结束后再送回表的所有者。表以 FP8 存取。
  • 多模态。ViT 放在 LLM 参数树之外，每步分三段执行：ViT 前向、LLM 前后向、ViT 反向，LLM 部分保持纯文本时的并行方式。超长、图像密集的序列把图像按上下文并行的 rank 均衡切分，每张图只读一次。对比学习阶段，图文特征的 all-gather 与前向、反向计算重叠。

要支撑全词表 OPD 的工程：教师权重放在集中式分布式存储里，前向时按需加载，并做类似 ZeRO 的切分；不物化几十万维的 logits，只缓存教师最后一层的隐藏状态，训练时再过一遍对应的输出头，现场重建 logits；样本按教师排序，保证一个 mini-batch 内每个教师的输出头只加载一次、显存里最多同时只有一个；精确 KL 用专门的 TileLang kernel 计算V4 §5.2.2。

支撑后训练的基础设施

  • 可抢占、可容错的 rollout。集群上的任何任务都可能被抢占。每个生成请求维护一份按 token 记录的预写日志（WAL），抢占时保存未完成请求的 KV，恢复后接着解码；硬件故障时用 WAL 里的 token 重新 prefill。报告特别指出，被打断后从头重新生成在数学上是错的：短回答更容易在中断前完成，从头生成会让分布偏向短序列V4 §5.2.3。
  • 百万 token 的 RL。rollout 数据拆成轻量元数据和按 token 存储的重字段：元数据整体加载，用于全局打乱和打包；重字段经共享内存加载器按 mini-batch 读入，用完即释放。
  • DSec 沙箱。由三个 Rust 组件组成：网关（Apiserver）、单机代理（Edge）、集群监控（Watcher），运行在 3FS 之上。一套 Python SDK 背后有四种执行底座：预热容器池上的无状态函数调用、兼容 Docker 的容器（EROFS 按需加载镜像层）、Firecracker microVM、QEMU 全虚拟机，切换只需改一个参数。每个沙箱有全局有序的命令轨迹日志：训练被抢占后恢复时，直接回放已完成命令的缓存结果，避免重复执行非幂等操作V4 §5.2.5。DSec 的独立论文给出的生产数字是：一个约 160 节点的单元每天服务约 300 万个沙箱，支撑 38 万并发，每秒创建 5000 个以上DSec。

12.5 V4.1：算法不变，数据和环境决定一切

V4.1 报告明确说，这一版的后训练没有引入新算法，仍是标准的 SFT → RL → OPD；在“固定且平平无奇的优化过程”下，几乎全部收益都来自合成数据和环境在规模、多样性和可验证性上的系统性改进V4.1 §5.1。

  • 任务即三元组。每个任务被形式化为（问题，环境，验证系统），从难度和正确性两个维度评估质量，并把这两者当作奖励，训练模型去构造更好的任务。任务在每次被新的 RL 运行使用后，都会根据新产生的轨迹重新审计。
  • 代码智能体环境的构建。来源有两个：内部员工和合作方的编码智能体会话（只保留很复杂、或模型表现很差的任务），以及超过一定星数的 GitHub 仓库。构建由多个智能体协作完成：第一个判断项目能否在容器里构建、运行和自动验证，选定起点提交，设计实现方向和 fail-to-pass / pass-to-pass 检查点；第二个装依赖、写测试和任务描述、做自测、清除泄露答案的痕迹，并打包成新的镜像层；然后多个不同的智能体尝试求解，由独立的质检智能体审查环境和求解轨迹（事实错误、检查点与描述不符、可被投机的漏洞）；不通过就交给修复智能体，修完重新验证。
  • 通用智能体环境。根据员工和合作方自愿回传的工作流数据，大规模模拟真实工具（SaaS、企业应用、业务后端）的接口和行为；同时收集员工提交的失败案例，复现失败场景，针对性地做 RL。
  • 跨脚手架 RL。rollout 拆成两部分：一个跑脚手架和工具的“智能体沙箱”，一个与脚手架无关的“worker 容器”，后者负责编排、把各种交互统一成同一种轨迹格式，并与 trainer 通信。实际在多个版本的 Claude Code，以及 OpenCode、Pi、DeepSeek Harness 等异构脚手架上联合训练，性能随 RL 步数持续上升。相继的 RL 运行之间用模型合并重新初始化，把不同路径上学到的改进合在一起。
  • 可连续调节的推理强度。系统提示里写 Reasoning Effort: {b}，b∈{1,…,100}b\in\{1,\dots,100\}b∈{1,…,100}。对每个提示，在若干档 bbb 上分别采样；同一 (x,b)(x,b)(x,b) 的响应组成一个子组，只在子组内做均值中心化，不同档位之间不直接比较。长度惩罚随 bbb 指数衰减：

  • 异步 RL。rollout 和训练放在同一批卡上分时执行。每个任务设定在途样本数上限，按“样本级”派发：新完成的样本数一凑够下一个提示的 GRPO 组大小，就派发这个提示。报告说按 batch 派发会让训练指标剧烈振荡，按提示派发又容易被组内长尾样本卡住。训练会抢占 rollout，打断发生在 token 边界上；KV 缓存和专家路由按 token 持久化，换上新 checkpoint 后直接接着生成。跨越多个 checkpoint 的样本，把每一段的路由拼接起来使用（concatenated routing replay）。
  • 异步的两个副作用。一是长度偏差：短样本先完成，会主导早期的 batch。对策是按数据集限制并发，以及丢弃过早返回的短样本。二是离策略：对策是限制最大离策略比例，并用损失掩码去掉过于陈旧的 token。
  • 最终 OPD使用 40 个以上、架构可以互不相同的教师。训练中可以动态调整数据配比、并发上限和启用的教师。
  • DSec 的扩展。并发沙箱达到数百万个。不用 Kubernetes，改用多个互不同步的放置引擎副本，只要求最终一致，由各节点按本地阈值硬性拒绝超额放置。用 sub-NUMA 分区，把每个 worker VM 绑定到一个 NUMA 域，单机容器密度从约 1000 提高到 2500 以上。RL 中观察到智能体利用新近披露的漏洞（XFS 权限问题、AppArmor 非法内存访问、从软件包镜像服务泄露答案），或者删掉关键二进制、甚至删掉整个文件系统；对策是每个沙箱一份 AppArmor 配置，加上基于 eBPF 的网络策略。环境被弄崩就记为失败轨迹，并给 RL 框架回传一个“后果”信号V4.1 §5.1.3。

13 · 推理与部署

KV 缓存怎么管、存到哪、丢了怎么补

13.1 V3 的部署形态

V3 起采用 prefill 和 decode 分离部署。Prefill 的最小单元是 4 节点 32 卡：注意力用 TP4 + SP + DP8，MoE 用 EP32，另放 32 个冗余专家，按统计到的高负载专家定期调整。Decode 的最小单元是 40 节点 320 卡：注意力 TP4 + SP + DP80，MoE 用 EP320，每卡放一个专家，另有 64 张卡放冗余专家和共享专家V3 §3.4。

13.2 V4：异构 KV 缓存

V4 的一层可能是 CSA、HCA 或纯滑窗，各类 KV 大小不同，滑窗还有自己的淘汰规则，PagedAttention 的假设不再成立。V4 把缓存分成两部分V4 §3.5：

  • 状态缓存。每个请求一块固定大小的空间，存最近 nwinn_{\text{win}}nwin​ 个滑窗 entry，以及凑不满一个压缩块、暂时还不能压缩的尾部 token。可以把这部分看成一个只依赖当前位置的状态空间模型。
  • 经典分块缓存存放 CSA/HCA 的压缩 entry。每块覆盖 lcm(m,m′)=128\mathrm{lcm}(m, m') = 128lcm(m,m′)=128 个原始 token，对应 32 条 CSA entry 和 1 条 HCA entry。KV 布局和稀疏注意力 kernel 是一起设计的。

落盘的前缀缓存。CSA/HCA 的压缩 entry 全部存盘，命中时一直复用到最后一个完整的压缩块，尾部不完整的块重算。滑窗 KV 在每层都有，体积约为压缩 KV 的 8 倍，所以给出三种策略：全存（零重算，但 SSD 写多读少）；每 ppp 个 token 存一个检查点（存储和重算可调）；完全不存，命中时重算最后 nwin⋅Ln_{\text{win}}\cdot Lnwin​⋅L 个 token（因为第 lll 层的滑窗只依赖上一层最近 nwinn_{\text{win}}nwin​ 个位置）。

13.3 V4.1：滑窗 KV 不再落盘

线上数据显示，滑窗 KV 只在一次活跃会话的几分钟内会被复用，而全局 KV 的复用有很长的尾巴。V4 部署中，滑窗 KV 占了持久化缓存将近一半；而 V4 的“完全不存”方案要求精确重算 L×nwinL\times n_{\text{win}}L×nwin​ 个 token，在生产中代价太高。V4.1 的做法是V4.1 §3.2：

  • 全局 KV 留在 SSD 上的持久化缓存里，保证至少存活 72 小时；滑窗 KV 移到一个用每台机器 10% 主机内存组成的分布式内存池，TTL 只有几分钟。持久化缓存因此缩小到 V4 的 1/8：去掉滑窗约减半，全局 KV 又压到 1/4。
  • 编码器滑窗的有界回放。全局 KV 命中而滑窗 KV 缺失时，只回放前缀的最后 nwinn_{\text{win}}nwin​ 个 token，并把滑窗截断在回放段内，得到近似的滑窗状态。
  • 解码器滑窗的有界回放。CED 下，prefill 本可以在编码器结束，唯一的障碍是解码器自己的滑窗 KV。V4.1 每次 prefill 只把提示词最后 nwinn_{\text{win}}nwin​ 个 token 的编码器输出送进解码器层，生成的滑窗 KV 只用于解码，不进入前缀缓存。后训练时也模拟这种回放，让模型提前适应。
  • 部署上把视觉编码、prefill 和 decode 三者分离（EPD）。由于 kernel 融合，大多数层（处于 Reuse 模式的层）prefill 只需 15 个 kernel，decode 只需 11 个。
